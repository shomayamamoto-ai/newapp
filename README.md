# snsauto — SNS運用自動化ツール

市場分析 → 台本 → 絵コンテ → 画像生成 → 映像生成 → 投稿 → 分析 → 改善 → データ蓄積 を
ひとつのパイプラインで一貫実行するツール。TikTok / YouTube / Instagram / X 対応。

```
research ─▶ structure ─▶ script ─▶ storyboard ─▶ narration ─▶ visuals ─▶ video ─▶ publish ─▶ metrics ─▶ A/B ─▶ PDCA ─▶ report
   │           │            │           │            │           │          │         │          │        │       │        │
競合上位50件  構成/テロップ   台本      絵コンテ    TTS＋尺の   3モードで  ワンタッチ 予約投稿   自動収集  勝ち筋  仮説検証 HTML/PDF
   分析         分析                                再調整      映像生成    編集      自動実行            の確定
```

各ステージは個別に実行でき、出力はすべてDBに永続化されるため、途中から再開できます。

## クイックスタート

```bash
pip install -e ".[llm,web,pdf,storage]"
snsauto init                       # 最初に一度だけ
snsauto project create ブランド名
snsauto doctor                     # 何が足りないかと、次にやることを表示
snsauto serve                      # http://127.0.0.1:8000
```

`snsauto init` と `snsauto doctor` は、いずれも最後に**次にやること**を出します。
Web UI のダッシュボードにも同じ手順がチェックリストで出るので、どちらから始めても
迷いません。

**接続情報が無い状態でもエラーで止まりません。** 何が足りず、どう設定すればよいかを
日本語で表示します。

```
YOUTUBE の接続情報がありません
  投稿と視聴維持率は /accounts からの連携が必要です。
  YOUTUBE_API_KEY（検索・コメント取得用。Google Cloud コンソールで発行）を設定してください。
    設定例は .env.example にあります。現在の状態は `snsauto doctor` で確認できます。
```

技術的な詳細が必要なときは `--debug` を付けると、従来どおりのスタックトレースが出ます。

## 認証情報が無くても動く範囲

`ANTHROPIC_API_KEY` もSNSの認証情報も無い状態で、以下は**そのまま動きます**：

| 機能 | 状態 |
|---|---|
| 競合データのCSV取り込み・スコアリング・上位ランキング | ✅ |
| フック分類 / CTA検出 / テロップ密度 / ビート推定 | ✅ ヒューリスティック |
| カット検出（ローカル動画ファイルから編集リズムを計測） | ✅ ffmpeg |
| 台本・絵コンテの**構造**生成（尺配分・ビート数・タグ） | ✅ 文面は要人手 |
| 画像生成（プレースホルダ） | ✅ 尺とテロップ可読性の検証用 |
| 動画レンダリング（Ken Burns・テロップ焼き込み・BGM合成） | ✅ |
| HTML/CSSテンプレート・PDFレポート | ✅ |
| PDCA管理・判定・データ蓄積 | ✅ |

`ANTHROPIC_API_KEY` を入れると、台本・絵コンテ・構成分析・改善提案がClaudeによる生成に切り替わります
（構造化出力を使用、モデル既定は `claude-opus-5`）。キーが無い場合は自動でヒューリスティックに退避し、
**パイプラインは止まりません**。

## プラットフォーム対応の実際

各プラットフォームは「検索」「投稿」「実績取得」を**別々に**ゲートします。実APIがそうなっているためです。

| | 検索 | 定点ウォッチ | コメント本文 | 投稿 | 実績取得 | 必要なもの |
|---|---|---|---|---|---|---|
| **YouTube** | ✅ | ✅ | ✅ | ✅ | ✅ | 検索・ウォッチ・コメントはAPIキーのみ。投稿はOAuth2（`youtube.upload`スコープ） |
| **X** | ✅ | ✅ | △ | ✅ | ✅ | 検索はBearer。コメント（リプライ）は直近7日のみ。投稿はOAuth 1.0a |
| **Instagram** | △ | △ | ❌ | ✅ | ✅ | Business/Creator + Facebookアプリ審査。ウォッチは相手もビジネスアカウントの場合のみ |
| **TikTok** | ❌ | ❌ | ❌ | ✅ | ✅ | Content Posting API。アプリ審査前は投稿が `SELF_ONLY` に強制されます |

検索の絞り込みも一様ではありません。YouTube は期間・尺・並び順・地域をすべて
受け付けますが、Instagram のハッシュタグ検索は何も受け付けず、X は直近7日に
制限されます。**受け付けられなかった条件はランごとに記録され、画面に表示されます。**

### 正直に伝えるべき制約

- **TikTokにキーワード検索の公開APIは存在しません。** Research APIは承認された学術機関限定です。
  スクレイピングは利用規約違反なので、このツールは実装していません。代わりに
  `snsauto research import <csv>` で、手動収集またはデータベンダーから取得したCSVを取り込みます。
- **Instagramの検索はハッシュタグ検索のみ**（`ig_hashtag_search` → `top_media`）で、返却件数に上限があります。
- **Instagramの投稿は公開HTTPS URLが必須です。** Graph APIが動画を取りに来る仕様で、
  バイト列を直接POSTできません。自前のストレージにアップロード後、
  `extra={"video_url": ...}` でURLを渡してください。
- **Xの検索は有料ティアが必要**で、かつ**直近7日しか遡れません**（コードは完全実装済み）。
  これはコメント（リプライ）取得にも効きます — 1週間より古い投稿のリプライは取得できません。
- **競合の保存数・視聴維持率は、どのプラットフォームでも取得できません。** 各社の
  Insights APIは自社アカウントの投稿にしか開放されていないためです。自社投稿側
  （PDCA）では取得できます。
- **Instagram の競合参照（business_discovery）は相手がビジネス／クリエイター
  アカウントの場合に限られます。** 個人アカウントはAPIから見えません。

`snsauto doctor` が、いま実際に使える能力を表で出します。

## 市場分析（競合リサーチ）

### 何を「市場分析」と呼んでいるか

キーワード1語に対して上位N件（既定50件）を取得し、スコアで順位付けし、上位の
構成を分解して、集計値を出すところまでです。含まれないもの: 市場規模の推定、
広告出稿データ、検索ボリューム、オーディエンス属性。

### 母集団の絞り込み

既定の母集団は「関連度の上位N件」ですが、これは知りたいものとずれていることが
あります。YouTube では関連度順は確立した古い動画に偏るため、「今何が効いているか」
を知りたいなら期間を切る必要があります。

```bash
snsauto research run ブランド "ダイエット 朝食" --within-days 30 --duration short
snsauto research run ブランド "副業" --order date --comments
```

**プラットフォームが受け付けなかった条件は、その旨が表示されます。**
Instagram のハッシュタグ検索は絞り込みを一切受け付けないため、期間を指定しても
APIには届きません。黙って無視すると、レポートが実際には存在しない絞り込みを
示唆することになるので、ランごとに「適用した条件」と「無視された条件」を記録
しています。

**自社アカウントは必ず除外してください**（`SNSAUTO_RESEARCH_EXCLUDE_AUTHORS`）。
除外しないと、比較対象の母集団に自分が含まれ、自分が投稿するたびにベンチマーク
そのものが動きます。

### テロップ分析（画面内の文字）

**以前は、キャプションの文字数を「テロップ統計」と呼んでいました。**数字は正しく
ても、測っている対象が違っていました。現在は動画のフレームからOCRで実際の
テロップを読みます。

| 出力 | 意味 |
|---|---|
| `event_count` | テロップの枚数 |
| `coverage_ratio` | テロップが画面に出ている時間の割合 |
| `first_telop_sec` | 最初のテロップが出るまでの秒数（フックの速さ） |
| `avg_chars` / `avg_hold_sec` | 1枚あたりの文字数と表示時間 |
| `chars_per_sec` | 実測の文字密度 |
| `position_mix` | 上部／中央／下部の配分 |

信頼度（高／中／低）を必ず併記し、**低い場合は測定値でビートマップを置き換え
ません**。読めなかったときは「テロップが無かった」ではなく「測定できなかった」
と表示します。

日本語OCRには tesseract の日本語データが必要です:

```bash
apt-get install tesseract-ocr tesseract-ocr-jpn
```

`ANTHROPIC_API_KEY` があると、OCRでは原理的に取れない情報（文字色・太さ・
装飾・見出しか字幕か）を、保持時間の長いカードに限って読み取ります。

#### 競合動画の取得について

フレームを読むには動画ファイルが必要です。取得経路は3つあり、**どれを使ったかは
レポートに明記されます**。

- `api` — Instagram は公式APIが `media_url` を返すため、そのまま取得できます
- `local` — 運用者がワークスペースに置いたファイル
- `external` — 運用者が設定した外部ダウンローダ。**既定では無効です**

競合の動画をダウンロードしてよいかは各プラットフォームの利用規約の問題であり、
その判断は運用者が行うものです。既定では行いません。

### 数字の精度について

集計値は「正しく計算されているか」だけでなく「その件数で言えることか」を併記します。

**投稿時刻は、件数ではなくパフォーマンスで並べます。** 以前は投稿時刻の最頻値を
返していましたが、それは「みんなが投稿している時間」であって「伸びる時間」では
ありません。混雑したジャンルでは、最も投稿が多い枠が最も伸びない枠であることが
普通です。現在は各時間帯の投稿のエンゲージ率中央値で並べ、**3件未満の時間帯は
判定対象から外し**、全体中央値を上回った枠だけを推奨します。時刻は UTC ではなく
運用者のタイムゾーン（既定 Asia/Tokyo）で表示します。

**再生数が取れないプラットフォームの数字は「率」ではありません。** Instagram の
ハッシュタグ検索は再生数を返さないため、割る分母がありません。以前はインタラク
ション数を1000で割って1.0で頭打ちにしていたため、**1000以上のインタラクションを
持つ投稿がすべて同点(1.0)になり、上位の順位付けが機能していませんでした。**
現在は基準（`views` / `interactions`）を明示し、基準の異なる調査どうしは
比較できないと画面に表示します。

**中央値と四分位を先に出します。** 平均は1本のバズ投稿の値をほぼそのまま表示する
ためです。パーセンタイルは線形補間で計算します（最近傍だと、10件未満の調査では
p90が最大値と一致してしまいます）。

**「勝ちパターンの尺」は、勝った投稿が実際に入っている帯を返します。** 中央値を
先に取ってから帯に当てはめると、どの投稿も入っていない帯が返ることがあります
（20秒と3分の勝ち投稿の中央値は97秒＝「1-3分」）。件数が割れている場合は
「ばらつき」と表示し、推奨しません。

**件数に応じた信頼度を併記します** — 3件未満は判定不能、6件未満は参考値、
12件以上で十分。

### 定点ウォッチ（競合アカウント）

キーワード調査が「この話題で何が効くか」に答えるのに対し、定点ウォッチは
「この競合が今何をしているか」に答えます。

```bash
snsauto watch add ブランド @rival_channel --platform youtube --label "競合A"
snsauto watch sweep ブランド
```

2回目以降のスイープで前回との差分が出ます。エンゲージ率・再生数・フォロワー数・
尺・フックの構成比・投稿ペースの変化を測り、**±15%（ノイズ水準）を超えたものだけ**
を「変化した」と報告します。変化の理由は推測しません — このデータには入っていない
からです。

**本当の伸び速度は、2回スイープして初めて測れます。** 1回の観測から計算できる
のは「生涯の再生数 ÷ 経過日数」で、これは平均であって加速度ではありません
（初週で90万再生、その後2年で10万再生の動画と、2年かけて均等に100万再生された
動画が同じ値になります）。2回のスイープの差分を取ると、実際の期間における実際の
増分が出ます — 「いま伸びている competitor 投稿はどれか」に答えられるのはこちらです。

**フォロワー数はここでしか取れません。** キーワード検索はどのプラットフォームでも
フォロワー数を返さないため、フォロワー比のエンゲージ率は定点ウォッチの対象に
ついてのみ算出され、キーワード調査では `None` を返します（ランごとに意味が変わる
数字を出すより、無い方がましなためです）。

| | 定点ウォッチ | 経路 |
|---|---|---|
| YouTube | ○ | `channels.list?forHandle` → 最新動画 |
| X | ○ | `users/by/username` → `from:` 検索（直近7日） |
| Instagram | △ | `business_discovery`。相手がビジネス／クリエイターアカウントの場合のみ |
| TikTok | ✗ | アカウント参照APIが無い |

### コメント本文の分析

コメント「数」は post が多いか少ないかしか言いません。本文は視聴者が何を
まだ知らないかを言います。

```bash
snsauto research comments <run_id>
```

質問／要望／不満／称賛／その他に分類し、**いいね数順**に並べます。質問に付いた
60いいねは「同じ疑問を持つ人が60人いる」という意味で、これが次の動画の企画に
直結します。

取得可否: YouTube（APIキーのみで可）／ X（直近7日のリプライ）／
Instagram は自社投稿のみ／ TikTok は検索自体が不可。

### 音声・BGMの分析

「どの音源がトレンドか」は**公式APIでは取得できません** — TikTok には公開検索が
無く、Instagram のハッシュタグ系エンドポイントは音源情報を返さず、YouTube も
第三者の動画の音楽メタデータを公開していません。ランキングを作る正直な方法が
ありません。

取得した動画そのものからは測れるので、そちらを測っています: ラウドネス(LUFS)、
無音区間の割合、音声帯域(300〜3400Hz)のエネルギー比率、そこから推定した
「ナレーション主体／BGM主体／混在／無音」。**推定であることを出力自体に明記して
います**（`method` フィールド）。

### 音源の共通性（「どの音源がトレンドか」の実装可能な形）

**どの音源がトレンドかは公式APIでは分かりません。** TikTok には公開検索が無く、
Instagram のハッシュタグ系エンドポイントは音源情報を返さず、YouTube も第三者動画の
音楽メタデータを公開していません。ランキングを作る正直な方法がありません。

その下にある問いには答えられます — **集めた上位投稿のうち、どれが同じ音源を
使っているか。** ある曲がキーワード上位20件のうち7件を占めているなら、それは
何かが起きています。

```bash
snsauto research audio <run_id>
```

テロップ解析のために取得済みの動画をそのまま使うので、追加のダウンロードは
発生しません。各動画の音声を「周波数帯ごとのエネルギー推移」に還元し、
**開始位置のずれを探索しながら**照合します（2人の制作者が同じ曲の同じ秒数から
始めることはまずないため）。

合成音源での実測値：

| 条件 | 類似度 |
|---|---|
| 同一曲・6秒ずれ | 0.997 |
| 同一曲・音量-9dB | 1.000 |
| 同一曲・ナレーション被せ | 0.873 |
| 別の曲 | 0.417〜0.680 |

しきい値 0.80 はこの 0.193 の隙間に置いています。**実際の楽曲ライブラリで
検証した値ではありません**ので、運用に合わせて調整してください。

**できないこと**: 音源名の特定（公式APIが音源情報を返さないため）。
ナレーションが大きい動画ではBGMが埋もれ、同じ音源でも別グループになることがあります。

### どの指標が取れるか

`/capabilities`（接続状況）に、プラットフォーム×指標×自社/競合の一覧を出しています。

| 指標 | 自社 | 競合 |
|---|---|---|
| 再生数・いいね・コメント数 | ほぼ全て可 | YouTube / X は可 |
| シェア | Instagram / X / TikTok | X のみ |
| 保存 | Instagram / X | **X のみ**（ブックマーク数が公開） |
| 視聴維持率・平均視聴時間 | YouTube / Instagram | **全て不可** |

**競合の視聴維持率・保存数は、どのプラットフォームでも取得できません。**
各社のInsights APIが自社アカウントの投稿にしか開放されていないためで、
回避策はありません。実装の不足ではないので、UI上でもそう表示します。

**自社投稿の視聴維持率は取得できます**（以前は取得していませんでした）。
YouTube は Analytics API（`youtubeanalytics.googleapis.com`、
`yt-analytics.readonly` スコープ）から `averageViewPercentage` を取得します。
これは公開カウントを返す Data API とは別のAPIで、`videos.list` にどれだけ part を
足しても返ってきません。Instagram は `ig_reels_avg_watch_time` と
`reels_skip_rate` を使います。

**このスコープが追加される前に連携したアカウントは、再連携するまで維持率が
取得されません。**そのまま動作し、維持率だけが `None` になります
（0% ではありません — 「測っていない」と「誰も見なかった」は別の事実です）。

TikTok は Display API に視聴時間のフィールドが無いため、自社投稿でも維持率は
取得できません。

### 接続の実地確認

**このリポジトリのAPI呼び出しは、実際のAPIと通信したことがありません。**
アプリ資格情報が無いためです。そのギャップに対して2つ用意しています。

**1. 契約テスト**（`tests/test_api_contract.py`、27件）
実際の httpx スタックを通して組み立てたリクエストを捕捉し、各社の仕様と
突き合わせます。パラメータ名の誤り、存在しない指標名、認証ヘッダの付け間違い、
パーセントと小数の取り違えを、ネットワーク無しで検出します。

**2. 実接続の確認コマンド**

```bash
snsauto verify                      # 全プラットフォーム
snsauto verify -p youtube           # 1つだけ
```

**読み取り専用です。投稿・編集・削除は一切しません。** 本番アカウントに対して
実行して安全です。認証・検索・アカウント参照・実績取得をそれぞれ最小の呼び出しで
確認し、**どの項目が空で返ったか**まで表示します（「維持率対応」と
「このアカウントでは維持率がnullで返る」の違いは、見るまで分かりません）。
失敗時は原因と対処（再連携が必要 / スコープ不足 / レート制限）を表示します。

## 映像生成の3モード

各カットの画を、3通りのどれでも作れます。`SNSAUTO_VISUAL_MODE` か `--visual` で選択します。

| モード | 中身 | コスト | 必要なもの |
|---|---|---|---|
| `still` | 生成画像＋Ken Burnsズーム | 最小 | なし（プレースホルダで動作） |
| `animate` | 画像→動画生成AIで実際に動かす | 高 | `VIDEOGEN_ENDPOINT` |
| `footage` | 実写・ストック素材をカットに自動マッチ | ゼロ | `SNSAUTO_FOOTAGE_DIR` |
| `auto` | 設定済みの中で最良のものを自動選択 | — | — |

```bash
snsauto footage index ./clips        # 素材を実尺・解像度つきで索引化
snsauto create video 1 --visual footage --narrate
```

素材のマッチはキーワード重なり・縦横比・尺の収まりで採点します。1本の動画の中で
同じクリップを使い回さず、素材が足りない場合でも**直前のカットとは必ず別のクリップ**を選びます
（カットをまたぐ同一素材は事故に見えるためです）。ファイル名から自動でキーワードを拾い、
`clip.json` を置けば日本語のキーワードも付けられます。

`animate` は Runway / Kling / Veo / Luma いずれも同じ非同期形（POST→ジョブID→ポーリング→DL）
なので、ベンダー固有ではなくその形に対して実装してあります。1カットの生成に失敗しても
そのカットだけ静止画に落ちて、動画全体は完成します（どのカットがどう落ちたかは記録されます）。

## ナレーション（TTS）と尺の再調整

`--narrate` で台本の各行を音声合成し、**実際の発話長を測ってカットの尺を組み直します。**

台本の秒数は誰も読み上げる前に決めた見積もりなので、実際の音声とは必ずずれます。
そのまま書き出すとナレーションが途中で切れるか、無音が残ります。

音声トラックは各カットの尺ぴったりに無音を詰めて連結します。発話を詰めて並べると、
尺の長いカットの後でナレーションが前倒しになり、映像と音がずれていきます。

TTSが未設定でも再調整は動きます（1秒7文字の読み上げ速度で見積もり）。

## 予約投稿とワーカー

```bash
snsauto worker run                 # 常駐。予約投稿の実行と実績収集
snsauto worker run --once          # 1回だけ実行
```

- **予約投稿**: 時刻が来た投稿を実行します。投稿行はAPI呼び出しの前に排他ロックを取るので、
  ワーカーを2つ動かしても**同じ動画が二重投稿されることはありません**（公開投稿は静かに取り消せないためです）
- **実績収集**: 投稿後 1h → 3h → 6h → 12h → 24h → 48h → 72h → 1週間 と間隔を空けて収集します。
  ショート動画の勝敗は初日でほぼ決まるので、全投稿を毎時ポーリングし続けるのはAPI枠の無駄です

## 台本の独自性チェック

台本生成AIには競合のタイトル・キャプション・**動画から読み取ったテロップ本文**を
渡しています。構成を学ばせるためですが、文言をそのまま再現することを止めるものが
ありませんでした。クライアントのブランドで競合のフックをそのまま出すのは、
どれだけ数字が良くても取り返しがつきません。

生成後に競合テキストと照合し、**連続10文字以上の一致**があれば、一致した表現を
名指しして再生成します（「もっと独自に」では何を変えればよいか伝わらないため）。

判定は意味の類似度ではなく**連続一致の長さ**です。同じ話題なら語彙は重なって当然で、
それは話題であって流用ではありません。流用の印は、長く連続した一致です。

| 入力 | 判定 |
|---|---|
| 「朝食を抜くと逆に太る理由」（競合と同一） | 流用 |
| 「【衝撃】朝食を抜くと逆に太る理由とは？」 | 流用 |
| 「朝ごはんを食べないと、かえって体重が増えます」 | OK |
| 「朝食は大事です」 | OK |

全角・半角、大文字小文字、句読点や括弧を除去してから比較します（そこを変えるのが
素朴な文字列照合をすり抜ける方法だからです）。

再生成を2回試しても一致が残る場合は、**最も一致の少ない案を採用したうえで台本に
記録を残します**。無限にやり直すのではなく、人が読むべきものとして見えるようにします。

## 伸ばす仕組み: 自社の実績を次の台本に還流する

**これが無いと、100本作っても1本目と同じ品質の台本が出ます。**

以前は台本生成に渡していたのが「競合調査」と「ブランド設定」だけでした。
自社の投稿が何本伸びて何本外したかは、一切生成に反映されていませんでした。
つまり競合を真似る機械ではあっても、自分の結果から学ぶ機械ではありませんでした。

### 何を学ぶか

投稿ごとに「どういう選択をしたか」を取り出し、「それが何を稼いだか」と突き合わせます。

| 取り出す選択 | 例 |
|---|---|
| フックの型 | question / result / listicle …（競合分析と同じ分類器） |
| 尺 | 〜15秒 / 16〜30秒 / 31〜60秒 / 60秒超 |
| カット数 | 4カット以下 / 5〜8 / 9以上 |
| テロップ密度 | 低め / 標準 / 高め |
| 投稿時間帯 | 深夜 / 朝 / 昼 / 夕方 / 夜 |
| ナレーション・CTA | あり / なし |

成果は**公開24時間後の値**で揃えて比較します（古い投稿ほど累計が伸びるため）。

### 断定しないことが要点です

3本で「疑問形フックが効く」と言ってはいけません。

- **6本未満**では何も抽出せず、生成には何も渡しません
- 各選択肢が**3本未満**なら比較対象にしません
- ブートストラップでノイズ水準を超えた差だけを採用します
- 「Xは成績が悪い」は事実でも指示にならないので、**上振れした項目だけ**を渡します

12本あってもばらつきを超える差が無ければ「見つかりませんでした」と出し、
やはり何も渡しません。**4件のデータから作った助言は、助言が無いより悪い**からです
（そのとおりに実行されてしまいます）。

条件を満たすと、生成にこう渡ります。

```
# このアカウントの実績（自社の過去投稿から統計的に有意だったもの）
対象 10本。以下は偶然では説明しにくい差が出た項目です。
競合の構成より、こちらを優先してください。
- フックの型が「question」の投稿は、それ以外よりエンゲージ率が+168%高い（5本 vs 5本）
- このアカウントの動画は 3秒、7秒 で視聴者が離脱しがちです。その時間帯の構成を変えてください。
```

どの知見がどの台本に効いたかは `Script.playbook` に記録され、画面でも確認できます。

## 納品物の品質: 出荷前チェック

レンダリングして、そのまま投稿していました。テロップがはみ出していても、
フックが4秒目にあっても、音量が基準外でも、誰も気づかないまま公開されます。
気づくのは翌日の維持率カーブで、その時には投稿は使い切っています。

### しきい値を発明していません

ほぼ全ての判定基準を、**このツールが既に実測しているもの**で較正しています。

- **競合上位の実測値** — この調査のキーワードで実際に効いている投稿のテロップ密度・
  カット間隔・尺
- **このアカウントの維持率** — 過去の視聴者が実際に離脱した秒数

どちらも無い場合、その項目は**黙ります**。発明した数値で良い動画を弾くゲートは
オフにされ、そうなると何も守りません。

```
[要修正] 4.6秒: URL「https://example.com/very/long/…」が複数行に分断されています
         日本語は任意の位置で改行できるためURLも途中で折られます。
         分断されたURLは読むことも入力することもできません
         → URLは短縮するか、テロップから外してキャプションに置いてください

[警告]   3.4秒: 12字を1.8秒しか表示していません（毎秒6.7字）
         この調査の競合上位は毎秒3.4字です。読み切れない可能性があります
```

### 止めるものと、伝えるだけのもの

**要修正（投稿を止める）** は、視聴者全員の端末で確実に見える不具合だけです。

- アスペクト比が媒体と違う（自動で切られるか余白が入る）
- URLが複数行に分断されている（読めず、入力もできない）
- 尺または解像度が0（書き出し失敗。そのまま投稿すればアップロードで失敗します）
- テロップが安全域の行数を超える

それ以外は警告で、投稿は止めません。止める場合も、了承すれば投稿できます。

**破損動画が通過していた穴も塞ぎました。** `probe` は読めないファイルに対して
例外ではなくゼロを返すため、書き出しが途中で失敗した動画が「空の動画」として
ゲートを素通りしていました。

## 視聴維持カーブの分析（離脱点の特定）

「冒頭で何秒に離脱したか」を秒単位で出す分析です。市販ツールは汎用データで較正した
**予測**を出しますが、こちらは**その動画の実測**を使います。

### なぜ自前のほうが精度で有利か

必要なものは2つあり、**両方とも既に持っています**。

**① 実測の離脱カーブ** — YouTube Analytics API の `audienceRetention` レポート
（`dimensions=elapsedVideoTimeRatio`、`metrics=audienceWatchRatio`）。自社動画のみ、
`yt-analytics.readonly` スコープが必要です。有料流入は離脱の仕方が違うため
`audienceType==ORGANIC` に絞っています。

**② その瞬間に画面に何が出ていたか** — これが決定的です。**動画を作ったのは
こちらなので、何秒に何のテロップが出て何秒でカットが変わるかを、推測ではなく
設計値として持っています。** 完成したMP4を解析するツールは、ここを毎回推定し直す
必要があります。

この2つを重ねると、こうなります。

```
冒頭3秒の残存は78%です。最大の離脱は 6.5秒 で、18%が離れています。
そこは4カット目（テロップ「まずはタンパク質から」10字を5.8秒表示）です。

  6.5s  -18%  → 4カット目「まずはタンパク質から」10字/5.8秒
  2.2s  -16%  → 1カット目「朝食を抜くのは逆効果」10字/2.5秒

  ・6.5秒: 同じ画が5.8秒続いています。
```

```bash
snsauto metrics retention <publication_id>
```

**さらに、較正されるのはそのクライアントの視聴者です。** 汎用ツールは他人の視聴者で
較正されています。代理店運用では、B社の視聴者はA社の視聴者ではありません。

### 記述と傾向を区別します

**1本のデータは、その1本についての記述です。** 3秒の離脱が1本で起きたのはその動画の
話で、6本で起きたら形式の話です。`mode` が `description` か `pattern` かを必ず
出力し、6本未満では傾向として扱いません。PDCAの判定と同じ考え方です。

粗いカーブでは冒頭の残存を**補間して**求めます。サンプルが0秒地点しか無い場合、
そこは定義上100%なので、そのまま返すと**どの動画もフックが完璧という結果**になります。

### 取れないもの

- **競合動画の維持カーブ** — どのプラットフォームでも不可（Insights APIは自社のみ）
- **Instagram** — 平均視聴時間は取れますが、カーブは取れません
- **TikTok** — Display APIにはどちらもありません

つまりこの分析はYouTubeの自社動画限定です。ただし構成の学習はプラットフォームを
またいで効くので、YouTubeで測った「何秒で離脱するか」はTikTok/Reelsの台本にも
反映できます。

## PDCA の判定精度

判定は「平均が動いたか」ではなく「その差がこの本数で言えるか」で出します。
4つの条件をコード側で強制します。

### 1. 成熟していない投稿は両側から除外します

公開3時間後の投稿はまだ数字が伸びきっていません。ベースラインに混ぜると
ベースラインが下がり、**次のサイクルが自動的に「成功」になります。**
公開24時間未満の投稿は除外し、何本除外したかを表示します。

### 2. 同じ「経過時間」の値どうしを比べます

累計再生数は、長く公開されている側が必ず有利です。スナップショット履歴から
**両群の「公開24時間後の値」**を読み出して比較します。この履歴は以前から
収集していましたが、判定には使われていませんでした。

### 3. プラットフォームを跨いで平均しません

YouTube のエンゲージ率は「インタラクション÷再生数」ですが、Instagram には
割る再生数がありません。平均すると比率と実数の平均になり、量として成立しません。
サイクルの投稿が特定のプラットフォームに8割以上偏っている場合、その中だけで
比較します。

### 4. 差がばらつきを超えたときだけ「改善した」と言います

ブートストラップ法で差の90%信頼区間を出し、**区間がゼロを含まない場合のみ**
成功と判定します。t検定を使わないのは、n=4で正規分布を仮定しても、その仮定が
結論のすべてを決めてしまうためです。リサンプリングは分布を仮定しません。

必ず併記するのが**ノイズ水準（この本数で判別できる最小の差）**です。

```
測定した変化 +3% に対し、この本数で判別できるのは 3%以上 の差までです。
90%信頼区間 [-0.0005, +0.0035] — ゼロを含むため、差があるとは言えません
あと約4本投稿すれば、この差を判定できる見込みです。
```

**目標値に届いても、差がノイズの範囲内なら success ではなく partial にします。**
再現しない勝ちを実績として積み上げないためです。

判定に必要な追加本数が現実的な範囲（40本）を超える場合は、本数を提案せず
**「この差は追いかける価値があるほど大きくない」**と表示します。

### 誤検出率の検証

同一分布から2群を抽出して「有意」と判定される割合（＝誤検出率）を、
サンプルサイズ3〜20で各400回測定しました。結果は 6.5%〜13.2% で、
90%信頼区間が想定する約10%と整合しています。この校正はテストで固定されており、
手法を変更すると検出されます。

## A/Bテスト

```bash
snsauto ab create mybrand 12 --dimension hook --arms 3
snsauto ab attach 1 B 45 46 47      # 案Bに投稿を紐づけ
snsauto ab review 1
```

**1回のテストで変える条件は1つだけ**です（`hook` / `telop_density` / `duration` / `cta` / `hashtags`）。
フックも尺もタグも同時に変えたテストは「この動画が伸びた」しか教えてくれず、
次に何を再現すればいいのか分かりません。案Aは常に対照群（元の台本そのまま）です。

勝者判定は保守的です。同じ内容の動画でも実績は3割くらい平気でばらつくので、
**各案が最低3投稿あり、かつ差が案の内部のばらつきより大きいとき**にだけ勝ちを宣言します。
それ以外は理由を添えて `inconclusive` を返します。

## アカウント連携と自動投稿

各SNSの**公式API**でアカウントを接続します。接続後はそのアカウントとして自動投稿できます。
スクレイピングや自動操作は一切行っていないため、規約の範囲内で運用できます。

```bash
snsauto serve      # → /accounts から各SNSを接続
```

| プラットフォーム | トークンの寿命 | 自動更新 | 投稿上限 |
|---|---|:--:|---|
| YouTube | アクセス約1時間／リフレッシュは無期限 | ✅ | APIクォータ単位（本数ではない） |
| TikTok | アクセス24時間／リフレッシュ365日 | ✅ | 1日25本・アップロード開始は毎分6回 |
| Instagram | 長期トークン60日（更新して延長） | ✅ | API側に問い合わせて残量を確認 |
| X | OAuth 1.0a（期限なし） | 不要 | プラン依存 |

接続に必要なアプリ資格情報:

```ini
YOUTUBE_CLIENT_ID= / YOUTUBE_CLIENT_SECRET=      # Google Cloud
TIKTOK_CLIENT_KEY= / TIKTOK_CLIENT_SECRET=       # TikTok for Developers
FACEBOOK_APP_ID=  / FACEBOOK_APP_SECRET=         # Instagram は Facebook アプリ経由
X_API_KEY=        / X_API_SECRET=                # X Developer Portal
SNSAUTO_PUBLIC_BASE_URL=https://...              # 承認後の戻り先（各社に登録する）
```

**トークンは自動更新されます。** ワーカーが期限の6時間前に更新するので、常時稼働でも
止まりません。TikTokは24時間で失効するため、これが無いと翌日には投稿できなくなります。
更新に失敗した場合はアラートとメールで通知されます。

**投稿上限はアプリ側でも数えています。** 上限に達した投稿は失敗ではなく「延期」として
予約状態のまま残り、枠が空いた次のtickで自動的に再試行されます。上限に当たってから
リトライを繰り返すと、その日の枠をエラーで使い切ってしまうためです。
Instagramについては、ドキュメントの数字（25／50／100）が食い違うため、
`content_publishing_limit` でアカウント自身の残量を問い合わせます。

### 接続までの手順と、その先の審査

各社の審査は、通っていなくても**APIが成功を返す**のが厄介なところです。
YouTube と TikTok は監査前でも投稿が成功し、動画IDまで返りますが、実際には
非公開に固定されています。気づかないまま非公開の動画が溜まります。

```bash
snsauto setup gates               # 各社の審査と、通るまで何が止まるかの一覧
snsauto setup connect instagram   # 接続までの手順を依存順に、現状つきで表示
snsauto setup review-pack instagram   # アプリ審査の申請文と録画手順を書き出す
```

| 媒体 | 審査 | 通るまで何が起きるか |
|---|---|---|
| Instagram | アプリ審査 + ビジネス認証 | 他社アカウントを連携できない（自分のアカウントは開発モードで可） |
| YouTube | API利用コンプライアンス監査 | **アップロードした動画が全て非公開に固定される** |
| TikTok | Content Posting API の監査 | **投稿が「自分のみ表示」に固定される** |
| X | 有料ティア契約 | 検索APIが使えず競合調査ができない |

`snsauto setup connect <媒体>` は、ローカルで確認できるもの（アプリ資格情報、
戻り先URL、連携済みアカウント、付与された権限）は実際に確認し、
確認できないもの（相手のアカウント種別など）は「?」として確認方法を示します。
**推測で「済」とは表示しません。**

`snsauto setup review-pack instagram` が出力するのは、申請フォームに貼り付ける
英文の用途説明、権限ごとに呼んでいるエンドポイントの一覧、録画すべき操作の手順、
差し戻しの典型的な理由です。用途説明は**このツールが実際に呼んでいるコードから
起こしている**ので、申請内容と実装の食い違い（差し戻しの最大の原因）が起きません。
エンドポイント名・フィールド名・メトリック名がコード中に実在することは
テストで検証しています。

### Instagram を繋ぐまでの前提条件

Instagram だけは、アプリを作れば繋がるという構造になっていません。
**先に相手のアカウント側が3つの条件を満たしている必要があり**、ここを飛ばすと
認可画面までは進めても、連携できるアカウントが1件も出てきません。

| # | 条件 | 確認方法 |
|---|---|---|
| 1 | ビジネスまたはクリエイターアカウントである | Instagramアプリ → 設定 → アカウントの種類 |
| 2 | Facebookページと連携している | Instagramアプリ → 設定 → ページとリンク |
| 3 | そのFacebookページの管理権限を持っている | Facebookページ → 設定 → ページの役割 |

3つが揃ってから `snsauto serve` → `/accounts` → Instagram を接続します。
接続時に要求する権限は6つで、それぞれ何のために必要かは
`snsauto verify -p instagram` が表示します。

| 権限 | これが無いと |
|---|---|
| `instagram_basic` | アカウントと投稿を参照できない |
| `instagram_content_publish` | リールを投稿できない |
| `instagram_manage_insights` | **リーチ・保存・シェア・平均視聴時間・スキップ率が全て取れない** |
| `pages_show_list` | 連携先のFacebookページを特定できない |
| `pages_read_engagement` | ハッシュタグ検索と競合アカウントの参照ができない |
| `business_management` | ビジネスアカウントとして操作できない |

3つ目が特に危険です。これが欠けていても**投稿は成功し、いいねとコメントは返ってくる**ため、
連携は正常に見えます。欠けているのは実績側だけで、しかもAPIはエラーではなく
権限エラーを返すだけなので、気づかないまま「この投稿は再生数0だった」という
記録が積み上がります。PDCAはその0を実測値として平均に入れてしまいます。

そのため、このツールでは次の2つを行っています。

- **接続直後に権限を検証します。** `snsauto verify -p instagram` の `scopes` チェックが、
  トークンが実際に持っている権限と必要な権限を突き合わせ、不足していれば
  「何が取れなくなるか」と併せて FAIL で表示します。投稿を1本もしていなくても
  確認できます（実績チェックの方は、読む対象の投稿が無いと確認できないためです）。
- **権限エラーをゼロとして保存しません。** インサイトが権限で拒否された場合、
  実績収集は例外を出してスナップショットを作りません。0件のデータより、
  データが無い方が正しいためです。投稿が古い・リールでないといった
  「その投稿の性質」による取得失敗とは区別しており、こちらは取れた数値だけ保存します。

#### 自社アカウントと、クライアントのアカウント

ここが代理店として運用する場合の分かれ目です。

- **自分（または開発者・テスターとして登録した人）のアカウント**は、
  Facebookアプリが開発モードのままで繋がります。審査は不要です。
  `showstagram.keio` を自分で試す場合はこちらで、その日のうちに動かせます。
- **クライアントのアカウント**を繋ぐには、アプリを公開モードにする必要があり、
  そのために **アプリ審査（App Review）とビジネス認証（Business Verification）** を通します。
  審査では上記の権限それぞれについて、実際の操作を録画した動画と用途の説明を求められます。
  ビジネス認証には登記情報などの書類が必要です。**通過まで通常2〜4週間**かかります。

つまり運用開始の逆算はこうなります。

```
今すぐ           自分のアカウントで接続・検証・投稿まで通す（開発モード）
　　↓            そのまま審査用の操作録画が撮れる
審査申請         権限ごとの用途説明＋操作動画＋ビジネス認証書類
　　↓            2〜4週間
クライアント接続  公開モードで、相手にOAuth認可画面を踏んでもらうだけ
```

審査を待つ間も、自分のアカウントでの運用と、競合調査（ハッシュタグ検索・
競合アカウント参照）はそのまま動きます。止まるのは他社アカウントへの接続だけです。

### 複数アカウントの運用

1つのプラットフォームに複数アカウントを接続できます。プロジェクト単位でも、
全プロジェクト共通でも紐づけられます。

```bash
snsauto account list                    # 接続中のアカウントと期限
snsauto account limits                  # 投稿枠の消費状況
snsauto create all ブランド "キーワード" --publish tiktok        # tiktokの全アカウントに投稿
snsauto create all ブランド "キーワード" --account 1 --account 4  # 指定アカウントだけに投稿
```

Web UIでは投稿先をアカウント単位のチェックボックスで選びます。
上限に達したアカウントとトークンが失効したアカウントは選択できない状態で表示されます。

**投稿枠はアカウントごとに数えます。** 1つのアカウントが上限に達しても、
他のアカウントへの投稿は止まりません。実績の収集も、投稿したアカウントのトークンで行います
（別のアカウントのトークンでは同じ投稿IDが「見つからない」と返ってくるためです）。

## 代理店運用での安全装置

他社のアカウントを預かる前提での作りです。

### クライアント間の誤爆防止

**あるプロジェクトから、別プロジェクトに紐づくアカウントへは投稿できません。**
アカウントIDを明示しても拒否します。以前はこの検査が無く、A社の動画をB社の公式
アカウントに投稿できてしまいました — 古いタブ、コピーしたURL、選択ミスのいずれでも
起き得ます。

拒否は例外であって、対象からの除外ではありません。黙って飛ばすと「指定より少ない
宛先に投稿され、誰もそれに気づかない」状態になり、クライアントから連絡が来るまで
分かりません。

Webからの投稿は**ジョブを積む前に**検査します。ワーカー内で失敗させると、
通知はアラート一覧に出ますが、投稿ボタンを押した本人はその瞬間それを見ていません。

`project_id` が未設定のアカウントは「全プロジェクト共通」として意図的に共有されて
いる扱いなので、どのプロジェクトからでも使えます。画面上で共通であることを明示します。

### トークンの保存

**暗号化していません。** ファイル権限が唯一の防御です。そのため、DBファイルの
権限を umask 任せにせず、初期化のたびに `600` に設定し直します（バックアップからの
復元、ボリュームのマウント、`cp -p` でのコピーはいずれも権限を緩めうるため）。

所有者以外から読める状態になっている場合、接続状況ページに警告を出します。
**代理店運用では、このファイルを読める人はクライアントのアカウントとして投稿できます。**
暗号化が必要になった場合は言ってください。

### ワークスペースの容量

**自動削除は一切しません。** 削除は明示的なコマンドだけです。

```bash
snsauto workspace usage           # 何をどれだけ抱えているか
snsauto workspace clean           # 削除内容の確認のみ（既定）
snsauto workspace clean --apply   # 実行
snsauto workspace clean --older-than 14 --apply
```

既定の対象はキャッシュ系（競合動画・中間ファイル）だけで、**完成動画とレポートは
対象外**です。クライアントの納品物なので、`-c renders` と明示しない限り消えません。

空き容量が閾値を下回ると接続状況ページに警告を出します。ディスクが尽きると、
動画生成と予約投稿が同時に止まり、最初の兆候は「予約した投稿が出ていない」です。

## 公開ストレージ（Instagram投稿に必須）

Instagram は動画のバイト列を受け取らず、**こちらが渡したURLを Meta のサーバーが取りに来ます**。
つまり公開HTTPS URL が無いと投稿できません。2方式を用意しています。

```ini
# S3互換（AWS S3 / Cloudflare R2 / MinIO / Wasabi）
STORAGE_BACKEND=s3
S3_BUCKET=my-bucket
S3_ENDPOINT_URL=https://xxx.r2.cloudflarestorage.com   # AWSなら空
S3_ACCESS_KEY=... 
S3_SECRET_KEY=...
S3_PUBLIC_BASE_URL=https://cdn.example.com   # 公開バケット/CDNなら恒久リンク。空なら署名付き期限リンク

# 自前サーバーから配信
STORAGE_BACKEND=local
SNSAUTO_PUBLIC_BASE_URL=https://snsauto.example.com
```

`local` は追加契約が不要な代わりに、**localhost や自己署名証明書では動きません**
（Meta 側から到達できる必要があるため）。だから `SNSAUTO_PUBLIC_BASE_URL` は推測せず必須にしています。

ファイルは内容のハッシュをキーにするので、同じ動画を再アップロードしても重複しません。

## 失敗通知

無人運転は静かに壊れます。トークンが失効したワーカーは毎分リトライを続け、
その週の投稿が丸ごと無いことに後から気づく、というのが典型です。

```ini
ALERT_EMAIL_TO=ops@example.com
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USER=
SMTP_PASSWORD=
```

投稿失敗・トークン失効・生成エラーは、**ダッシュボードの「要対応」** と **メール** の両方に出ます。

同じ失敗の繰り返しは1行にまとめ、回数だけ増やします（同じメールが60通来るのは0通と同じです）。
メールは新規に開いたときだけ送り、「対応済み」にした後で再発したら改めて送ります。
再発は新しい情報だからです。

## Web UI

```bash
pip install -e ".[web]"

```

| 画面 | 内容 |
|---|---|
| ダッシュボード | 全プロジェクト横断の集計、最近の調査履歴 |
| 接続状況 | どのプラットフォームで何ができるか、ローカル環境（ffmpeg/Chromium/LLM）の状態 |
| プロジェクト | 調査・台本・動画・投稿・PDCAの一覧と実績サマリ |
| 調査詳細 | 上位50件のランキング、フック類型の分布、頻出タグ・語 |
| 台本詳細 | ビート表、絵コンテのカット一覧、**動画プレイヤー**、ダウンロード |
| PDCA詳細 | 仮説・目標・実測・判定・次アクション |
| A/Bテスト | 各案の変更内容・実績・勝者判定 |

| 要対応（ダッシュボード） | 投稿失敗・トークン失効などの未対応アラート |

ライトとダークの両方に対応します（OSの設定に追従）。
`/api/projects` `/api/runs/{id}` `/api/capabilities` でJSONも返します（`/api/docs` にOpenAPI）。

### 認証（サーバー公開時は必須）

DBにはSNSのアクセストークンが入り、UIからは課金の発生する生成と公開投稿ができます。
localhost 以外に出すなら認証を必ず有効にしてください。

```bash
snsauto user secret                          # SNSAUTO_SECRET_KEY 用の鍵を生成
export SNSAUTO_AUTH_ENABLED=true SNSAUTO_SECRET_KEY=...
snsauto user create you@example.com --role admin
```

| 権限 | 閲覧 | 調査・生成 | 投稿 |
|---|:--:|:--:|:--:|
| `viewer` | ✅ | — | — |
| `editor` | ✅ | ✅ | — |
| `admin` | ✅ | ✅ | ✅ |

パスワードは scrypt（標準ライブラリ）で保存、セッションはHMAC署名クッキー（サーバー再起動で
ログアウトされず、セッションテーブルも不要）、POSTは全てCSRFトークンを検証します。
ログイン失敗時は「メールアドレスまたはパスワードが違います」の一文だけを返し、
存在しないアカウントと同じ応答時間になるようにしてあります（アカウント列挙を防ぐため）。

### 実行と安全弁

調査・台本生成・動画生成・A/Bテスト作成・実績収集はブラウザから実行できます。
時間のかかる処理はジョブ行に積んでバックグラウンドで走らせ、UIは進行状況をポーリングします
（リクエスト内で走らせると、ブラウザがタイムアウトし、再読み込みで二重実行されるためです）。

**公開投稿だけは確認欄に `PUBLISH` と入力しないと実行できません。** 管理者権限も必要です。
取り消せない操作をワンクリックに置くのは妥当ではないためです。

動画と画像はDBに記録されたIDから解決して配信します。ワークスペースを静的ディレクトリとして
公開していないのは、細工したパスでディレクトリ外に出られるのを防ぐためです。

## 設計上の判断

**ランキングは再生数順ではありません。** フォロワー1000万のアカウントの200万再生は
「その構成が効く」証拠になりません。エンゲージメント率(55%)・伸び速度(27%)・到達(18%)の
合成スコアで並べ替えます。エンゲージメント重みは他2つの合計より**厳密に大きく**設定してあり
（コード内で `assert` 済み）、大アカウントの弱い投稿が小アカウントの強い投稿と同点になる事態を防いでいます。
レポートの重み表記はコードから渡されるので、数値がずれることはありません。

**テロップはASS字幕で焼き込みます。** SRTではなく縁取り・影・整列・セーフエリアを個別制御できるためです。
セーフエリアはプラットフォーム毎に変えています（TikTokは右側のアクションレールと下部キャプションで
画面が大きく隠れるため、marginを厚く取る）。日本語には空白が無いので、
禁則処理付きの文字幅ベース折り返しを実装しています。フォントはfontconfigから
実在するCJKフォントを解決します（未インストールのファミリを指定すると豆腐になるため）。

**PDCAはn=1で成功を宣言しません。** 3投稿未満は `inconclusive` を返し、
必要なサンプル数を明示します。ソーシャルの分散を考えれば、1本のヒットは仮説の証明になりません。

**スコアの正規化はlog圧縮してからmin-max**します。ソーシャル指標は裾が極端に重く、
素のmin-maxだと1本のバズが他全部を0付近に潰してしまいます。

## 配備

常時稼働サーバー向けに Docker Compose と systemd の両方を用意しています。
手順は [`deploy/README.md`](deploy/README.md) にあります。

```bash
docker compose up -d --build
docker compose exec web snsauto user create you@example.com --role admin
```

Web と worker は別プロセスです。**worker を止めると予約投稿と実績収集が止まりますが、
Web は動き続けるので気づきにくい**点に注意してください。

Nginx 設定（`deploy/nginx.conf`）は TLS 終端、`X-Forwarded-Proto` の受け渡し、
レンダリング待ちに耐える 600 秒のタイムアウト、大きな動画のための `client_max_body_size 512M`
を含みます。

### スキーマ移行

起動時に自動でマイグレーションが走ります（Alembic）。

```bash
snsauto db current      # 適用済みリビジョン
snsauto db upgrade      # 最新まで適用
snsauto db revision -m "add column"   # モデル変更から自動生成
```

`create_all` ではなくマイグレーションにしているのは、**既存テーブルへの列追加ができない**ためです。
蓄積したデータを持つ常時稼働の環境では、スキーマ変更のたびに壊れます。
移行前に作られたDB（バージョン印の無いもの）は、テーブルを作り直さず印を打つだけで取り込みます。
